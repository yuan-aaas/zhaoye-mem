## 2. 已定决策

| # | 决策 | 理由 | 影响 |
|---|---|---|---|
| D1 | 数据根 `schema_version = 1`，布局见 §3；旧的 `journal/`、`projections/` 布局**不迁移** | 旧布局从未发布，且其事实源模型已被 ADR 0002 取代 | 检出旧布局 → `SCHEMA_MIGRATION_REQUIRED`，`doctor` 提示手工处理 |
| D2 | 人格用一个 `identity.json` 装五段，段各有 `revision`，文档有全局 `revision` | 跨段一致性只需一次原子替换；省掉多文件事务 | 文件上限 256 KiB；超限再考虑拆文件 |
| D3 | 写入协议 = `operation_id` 幂等 + `expected_revision` CAS + 串行队列 + 临时文件 rename | 单进程可证明的原子性与幂等；不引入全局日志 | 所有写路径必须走 `IdentityStore.commit` |
| D4 | 内核更新必须带 `user_confirmed.confirmation_ref`，且与画像更新使用不同方法 | 落实 I4；让“谁确认的”可追溯 | 无凭据 → `UNAUTHORIZED`，不落盘 |
| D5 | 幂等回执落在 `identity/operations.jsonl`，**不是事实源**，有界轮转 | 重复 `operation_id` 需要返回原回执；但权威仍是 `identity.json` | 最后一行残缺可忽略；中间行损坏 → `CORRUPT_DATA` |
| D6 | 序列化用契约里的 `serializeIdentityDocument()`，哈希由 `storage` 用 `node:crypto` 计算 | 保证“写入字节 = 校验字节 = 回执哈希”；core 不碰 node 内建模块 | 序列化必须稳定：固定键序、2 空格缩进、末尾换行 |
| D7 | 契约删除 `events.ts`；`memory.ts` 拆为 `backup.ts`；新增 `limits.ts`、`defaults.ts` | 事件信封是旧 journal 方案残留；上限与默认值要成为唯一事实源 | 破坏性变更，仅内部使用，无外部兼容负担 |

未决事项见 §11，其中只有“内核默认文案”会阻塞 init 的最终内容，不阻塞其余工作。

## 3. 数据根布局

```text
<data-root>/
├─ manifest.json                     # 见 §4.4
├─ identity/
│  ├─ identity.json                  # 权威数据，UTF-8，无 BOM
│  ├─ identity.md                    # 派生投影
│  ├─ versions/000000000001.json     # 不可变快照，12 位零填充
│  ├─ versions/000000000002.json
│  ├─ versions/index.jsonl           # 快照元数据（含已淘汰的 retained:false）
│  └─ operations.jsonl               # 幂等/操作回执，超过 2000 行轮转为 operations.1.jsonl
└─ presence/
   ├─ owner.json                     # 当前活跃实例
   └─ last-released.json             # 最近一次离开/接管（可无限覆盖）
```

约定：

- 所有文件 UTF-8、`\n` 换行、无 BOM；时间一律 ISO 8601 带时区（统一写 UTC `Z`）。
- 不允许在数据根内出现 `.tmp-*` 以外的临时文件；残留 `.tmp-*` 由下次写入清理，不视为损坏。
- 本阶段不创建 `backup/`、`assets/`；由 M2/M3 的 `ensureDataRoot` 按版本补齐。
- 目录与文件权限沿用系统默认；不额外做 ACL，也不把数据根放进同步盘（`doctor` 只提示，不阻断）。

### 4.2 身份文档与更新请求

文档形状见 [03 §3.1](03-记忆核心技术设计.md#31-人格记忆-jsonschema_version-1)，本节只补更新协议。

```ts
type SectionName =
  | 'safety_kernel'
  | 'user_profile'
  | 'character_profile'
  | 'project_state'
  | 'continuity_memory';

type EntryOp<T> = { op: 'upsert'; entry: T } | { op: 'remove'; id: string };

type IdentityUpdate =
  | { section: 'safety_kernel'; principles: string[]; user_confirmed: { confirmation_ref: string } }
  | {
      section: 'user_profile';
      display_name?: string | null;
      facts?: EntryOp<ProfileEntry>[];
      preferences?: EntryOp<ProfileEntry>[];
    }
  | { section: 'character_profile'; traits: EntryOp<ProfileEntry>[] }
  | { section: 'project_state'; projects: EntryOp<ProjectEntry>[] }
  | { section: 'continuity_memory'; entries: EntryOp<ContinuityEntry>[] };

interface IdentityCommitRequest {
  request_id: string;        // uuid
  operation_id: string;      // uuid，幂等键
  expected_revision: number;
  update: IdentityUpdate;
  reason: string;            // ≤200 字符，写入版本元数据
  evidence_refs: string[];   // ≤5，写入版本元数据
}

interface IdentityCommitReceipt {
  assistant_id: string;
  revision: number;
  section_revisions: Record<SectionName, number>;
  operation_id: string;
  applied_at: string;
  document_hash: string;     // identity.json 字节的 sha256
  version_path: string;      // 相对数据根
  projection: { path: string; bytes: number };
  warnings: string[];        // 例如 projection_failed
}

interface IdentityCommitResult {
  receipt: IdentityCommitReceipt;
  replayed: boolean;         // true = operation_id 命中，返回原回执
}

interface IdentitySnapshot {
  document: IdentityDocument;
  revision: number;
  file_hash: string;
  projection_path: string;
}

interface ActorContext {
  adapter_id: string;        // 'cli' | 'dsh' | 'mcp'
  host?: string;
  session_id?: string;
  scope_id: string;          // M1 必须等于 assistant_id
  granted_project_ids: string[] | '*';
  granted_source_ids: string[] | '*';
}
```

语义：

- `expected_revision` 与当前全局 revision 不等 → `CONFLICT`（附 `current_revision`）。
- `operation_id` 已存在 → 原样返回回执，`replayed: true`，**不再加 revision**。
- 列表段用 `upsert` / `remove` 逐条操作；`upsert` 按 `id` 命中则替换整条，未命中则追加；`remove` 不存在 → `NOT_FOUND`（不静默）。
- `safety_kernel` 用整段替换原则数组，必须带 `user_confirmed`；`confirmation_ref` 是不透明字符串（终端确认哈希、宿主审批 ID 等），只做非空与长度校验。
- `reason` 与 `evidence_refs` 允许为空数组，但 `reason` 必填。

### 4.3 版本与操作记录

```ts
interface IdentityVersionRef {
  revision: number;
  at: string;
  section: SectionName;
  operation_id: string;
  reason: string;
  document_hash: string;     // 快照文件哈希
  retained: boolean;         // false 表示已被轮转淘汰（仅元数据保留）
}

interface StoredOperation {
  operation_id: string;
  request_id: string;
  adapter_id: string;
  section: SectionName;
  revision: number;
  at: string;
  receipt: IdentityCommitReceipt;
}
```

- 快照文件是完整文档，不是 diff；回滚与 `diff` 都从快照取。
- 保留策略：最近 200 个快照；内核变更的快照不参与淘汰。淘汰只删文件，`versions/index.jsonl` 保留元数据并把 `retained` 置 `false`。
- `operations.jsonl` 一行一个 `StoredOperation`；轮转后按 `operations.1.jsonl` → 当前文件顺序从旧到新查找。

### 4.4 manifest、错误与 presence 契约

```ts
interface DataManifest {
  format: 'zhaoye-data';
  schema_version: 1;
  assistant_id: string;      // uuid，创建时生成，永不修改
  created_at: string;
}

interface AdapterManifest {
  host_id: 'dsh' | 'mcp' | 'cli';

  capabilities: Array<'tools' | 'prompt' | 'session' | 'approval' | 'notice' | 'worker'>;
  adapter_version: string;

```

启动时把 `manifest.schema_version` 与 `host.data_schema` 比对：不相等 → `SCHEMA_MIGRATION_REQUIRED`，不读数据。

错误码见 [03 §6](03-记忆核心技术设计.md#6-错误模型与恢复)。`ZhaoyeError` 是 `Error` 子类，带 `code` / `retry` / `action` / `details`；每层只抛它，不用裸 `Error` 传到门面外。

`OwnerInfo` 保留现有字段（`host`、`host_name`、`pid`、`instance_id`、`session_id?`、`started_at`、`heartbeat_at`、`heartbeat_interval_ms`、`assistant_id`、`adapter_version`），新增 `state: 'active'` 字段便于未来扩展，构造时固定写 `active`。

## 5. 存储层设计（`packages/storage`）

### 5.1 模块划分与公开面

```text
packages/storage/src/
├─ index.ts                 # 公开面
├─ atomic-fs.ts             # readJson / writeAtomic / writeAtomicDurable / ensureDir
├─ paths.ts                 # 数据根路径解析、相对路径校验、Windows home 解析
├─ data-root.ts             # ensureDataRoot / openDataRoot / manifest 读写
├─ identity-store.ts        # IdentityStore 实现
├─ projection.ts            # 投影文件读写（只接受已经渲染好的字符串）
├─ operations-log.ts        # 追加、读取、轮转、尾部残缺处理
├─ presence.ts              # PresenceStore 实现
└─ internal/
   ├─ mutex.ts              # 进程内串行队列
   └─ fs-probe.ts           # 可写性、PID 存活探测
```

公开面（接口定义在 `packages/contracts/src/stores.ts`，`storage` 实现；`core` 只 import contracts）：

```ts
export interface IdentityStore {
  read(): Promise<{ document: IdentityDocument; fileHash: string; bytes: number }>;
  commit(input: CommitInput): Promise<CommitOutput>;
  listVersions(limit: number): Promise<IdentityVersionRef[]>;
  readVersion(revision: number): Promise<IdentityDocument>;
  readProjection(): Promise<string | null>;
}

export interface CommitInput {
  bytes: string;                 // serializeIdentityDocument 的结果
  document: IdentityDocument;
  expectedRevision: number;
  operation: OperationTemplate;  // core 组装，缺 hash/路径/投影字段
  projectionMarkdown: string;
}

type OperationTemplate = Omit<StoredOperation, 'receipt'> & {
  receipt: Omit<IdentityCommitReceipt, 'document_hash' | 'version_path' | 'projection' | 'warnings'>;
};

export interface CommitOutput {
  fileHash: string;
  bytes: number;
  versionPath: string;
  projection: { path: string; bytes: number };
  warnings: string[];
  operation: StoredOperation;    // 已补齐回执字段，随本次提交写入 operations.jsonl
}
```

`writeAtomic` 的算法（Windows 优先）：

1. 在目标同目录创建 `.<name>.tmp-<pid>-<random>`，写入全部字节，`FileHandle.sync()`。
2. `rename(tmp, target)` 覆盖目标（`fs.rename` 对文件是替换语义）。
3. POSIX 上再 fsync 父目录；Windows 不支持目录 fsync，跳过并记录在代码注释与文档，不假装成功。
4. `rename` 失败 → 删除临时文件 → `STORAGE_FAILURE`；删除也失败时保留临时文件并由下次写入清理。

读取：`readJson` 先读字节、再 `JSON.parse`、再 zod 校验；任一失败 → `CORRUPT_DATA`，`details.path` 指向文件。**不做静默修复。**

### 5.2 数据根打开守护表

| 打开时的状态 | 行为 |
|---|---|
| 路径不存在或空目录 | 允许 init：写 `manifest.json`、`identity/identity.json`、`identity.md`、首个版本快照；回报 `created: true` 并提示路径 |
| 有 v1 manifest + 合法身份文件 | 正常 open；revision 与快照不一致时由 `doctor` 报告 |
| manifest 存在但 `schema_version` 不是 1 | `SCHEMA_MIGRATION_REQUIRED`，不自动升级 |
| 存在 `journal/` 或 `projections/`（旧 v3 布局） | `SCHEMA_MIGRATION_REQUIRED`，`action: 'reinit'`，本阶段不迁移 |
| 有 `identity/` 或 `presence/` 但缺 manifest | `CORRUPT_DATA`，**绝不**初始化成空库 |
| 目录不可写或父目录不可写 | `STORAGE_FAILURE`，`action: 'run_doctor'`，不改用其他路径 |
| presence 被存活实例持有 | `ASSISTANT_PRESENT_ELSEWHERE`，`details.owner` 给出宿主、PID、开始时间 |

`init` 必须显式（CLI `zhaoye init`）或由 `createZhaoye({ initIfMissing: true })` 触发；命令自身要求目标目录为空或已有合法数据根，不做“猜路径”。

### 5.3 并发与原子性

- 进程内所有写经过一个串行队列（`internal/mutex.ts`），队列内完成“读当前 revision → 比较 → 写临时文件 → rename → 快照 → 操作记录 → 投影”。
- 跨进程依赖 presence 单活（§5.5）；presence 被绕过时不承诺一致性，`doctor` 会报告“数据根被非持锁进程修改”的迹象（`fileHash` 与操作记录最后一条不一致）。
- 快照写入失败不阻断已完成的 JSON 提交：回执 `warnings` 加 `version_failed`，`doctor` 提示可用 `operations.jsonl` 重建缺失快照。
- 操作记录追加使用 `O_APPEND` + `fsync`；崩溃留下的半行在读取时**只允许丢弃最后一行**，中间行损坏 → `CORRUPT_DATA`。

### 5.4 人格存储

- `read()` 返回文档、文件哈希、字节数；不返回投影。
- `commit()` 的顺序固定：CAS 复核 → 写 JSON → 写快照 → 追加操作记录 → 写投影。
- 投影失败只影响 `warnings` 与 `projection.failed`，不改变“JSON 已提交”的事实。
- 快照命名 `versions/<12 位 revision>.json`；先写临时文件再 rename，禁止部分写入。
- 淘汰在提交后异步执行（本次仍同步完成，避免并发）；被淘汰文件进 `versions/index.jsonl` 的 `retained: false`。

### 5.5 presence

```ts
type PresenceState =
  | { status: 'acquired'; owner: OwnerInfo }
  | { status: 'reentered'; owner: OwnerInfo }          // 同 pid + 同 instance，幂等
  | { status: 'taken_over'; owner: OwnerInfo; previous: OwnerInfo }
  | { status: 'blocked'; owner: OwnerInfo; reason: 'same_process' | 'alive' };
```

- `acquire`：读取 `owner.json`；
  - 不存在 → 原子写入新 owner，`acquired`；
  - 同 `pid` + 同 `instance_id` → `reentered`，不重写文件；
  - 同 `pid`、不同 `instance_id` → `blocked(same_process)` → `ASSISTANT_SAME_PROCESS`；
  - 不同 `pid`：存在且存活（`process.kill(pid, 0)` 成功）且心跳未过期 → `blocked(alive)` → `ASSISTANT_PRESENT_ELSEWHERE`；
  - 不存在、或已死亡、或心跳超过 3 个间隔 → 写 `last-released.json` 记录旧 owner 与原因，再原子写入新 owner，`taken_over`。
- `heartbeat`：每 60s 原子重写 `owner.json` 的 `heartbeat_at`；`instance_id` 不匹配 → `CONFLICT`（说明实例已被接管）。
- `release`：仅当 `instance_id` 匹配时删除 `owner.json` 并写 `last-released.json`；不匹配 → `CONFLICT`，不误删他人。
- PID 复用风险：以心跳时间为主判据，PID 存活只作为“不能接管”的保守信号；实现里把二者做成独立可测函数，便于测试注入假时钟与假探测。
- 空闲超时不进 M1（见 docs/README 待拍板 #3）。

## 6. 领域层设计（`packages/core`）

### 6.1 身份服务

```ts
export interface IdentityService {
  read(ctx: ActorContext): Promise<IdentitySnapshot>;
  preview(req: IdentityCommitRequest, ctx: ActorContext): Promise<IdentityPreview>;
  commit(req: IdentityCommitRequest, ctx: ActorContext): Promise<IdentityCommitResult>;
  rollback(req: IdentityRollbackRequest, ctx: ActorContext): Promise<IdentityCommitResult>;
  listVersions(ctx: ActorContext, limit?: number): Promise<IdentityVersionRef[]>;
}
```

职责边界：

- 校验 `ctx.scope_id === document.assistant_id`，否则 `OUT_OF_SCOPE`。
- 内核提交缺少 `user_confirmed`、或 `confirmation_ref` 为空 → `UNAUTHORIZED`；不因为“调用方是 CLI”就放行。
- 计算新文档：目标段 `revision + 1`、`updated_at = clock.now()`、全局 `revision + 1`、`updated_at` 同步。
- 用 `serializeIdentityDocument()` 产出字节，组装 `OperationTemplate`（不含 hash/路径/投影字段），调用 `IdentityStore.commit`；storage 补齐回执字段并追加操作记录，core 把返回的 `StoredOperation.receipt` 作为回执。
- `preview` 只跑校验与 diff，不写盘、不占 `operation_id`。

### 6.2 更新语义与 diff

`IdentityPreview`：

```ts
interface IdentityPreview {
  base_revision: number;
  next_revision: number;
  changes: Array<{
    section: SectionName;
    added: string[];      // entry id 或原则摘要
    removed: string[];
    replaced: string[];
  }>;
  warnings: string[];     // 例如 low_confidence_entry
}
```

- `low_confidence_entry`：`source = 'model_inference'` 且 `confidence < 0.6` 时警告，不阻断。
- 同一请求里对同一 `id` 先 upsert 再 remove → `INVALID_INPUT`（顺序歧义必须显式拆成两次提交）。

### 6.3 投影渲染

`renderIdentityMarkdown(document)` 是纯函数，规则见 [03 §3.2](03-记忆核心技术设计.md#32-markdown-投影)：

- 输入相同、输出逐字节相同；不读取时钟，不使用本地化。
- 数字（confidence）固定保留一位小数。
- 标题层级与段落顺序固定，空段输出 `（空）`。
- 渲染结果只由 storage 写盘；core 不接触文件。

### 6.4 回滚

```ts
interface IdentityRollbackRequest {
  request_id: string;
  operation_id: string;
  expected_revision: number;
  section: SectionName;
  to_revision: number;
  reason: string;
}
```

- 读取 `versions/<to_revision>.json`；不存在（已淘汰）→ `CONFLICT`，`details.retained: false`。
- 只替换目标段，其他段保持当前值；产生**新的**全局 revision，历史不改写。
- 内核回滚同样需要 `user_confirmed`；否则 `UNAUTHORIZED`。

## 7. 门面与 CLI

### 7.1 组合根与门面（M1 子集）

```ts
export interface ZhaoyeConfig {
  dataRoot?: string;            // 默认 ~/.zhaoye
  host: AdapterManifest;
  clock?: ClockPort;
  initIfMissing?: boolean;      // 默认 true；只读命令传 false
}

export interface Zhaoye {
  readonly assistantId: string;
  identity: IdentityService;
  presence(): Promise<OwnerInfo | null>;
  doctor(): Promise<DoctorReport>;
  close(): Promise<void>;       // 释放 presence，幂等
}

interface DoctorReport {
  data_root: string;
  schema_version: number;
  assistant_id: string | null;
  revision: number | null;
  checks: Array<{ id: string; status: 'ok' | 'warn' | 'fail'; detail: string }>;
  presence: { state: 'active' | 'stale' | 'none'; owner: OwnerInfo | null };
}
```

- `createZhaoye` 是唯一 `new` 具体实现的地方；组合根在 `packages/app` 里 import `@zhaoye/storage` 构造 `IdentityStore` / `PresenceStore`（M1 需给 `packages/app/package.json` 增加该依赖），`core` 只接收 contracts 的端口接口。适配器只拿到 `Zhaoye`。
- 打开顺序：解析路径 → 读/建 manifest → 读人格 → 获取 presence → 构造服务；任一步失败原样上抛，不降级成“只读模式”。
- `close()` 释放 presence；重复调用返回成功；未持有的实例调用不误删他人 owner。

### 7.2 错误映射

| 场景 | code | action |
|---|---|---|
| 数据根被其他实例持有 | `ASSISTANT_PRESENT_ELSEWHERE` | `release_presence` |
| 同进程重复 open | `ASSISTANT_SAME_PROCESS` | `release_presence` |
| revision 不匹配 | `CONFLICT` | `run_doctor` |
| JSON/快照解析失败 | `CORRUPT_DATA` | `restore_backup` |
| 目录不可写、rename 失败 | `STORAGE_FAILURE` | `run_doctor` |
| schema 版本不符 | `SCHEMA_MIGRATION_REQUIRED` | `reinit` |
| 内核无确认凭据 | `UNAUTHORIZED` | — |
| scope 不匹配 | `OUT_OF_SCOPE` | — |
| 字段超限 | `INVALID_INPUT` | — |

门面只做映射与补充 `details`（路径、revision、owner），不改变 `code`。

### 7.3 CLI

| 命令 | 行为 | 退出码 |
|---|---|---|
| `zhaoye init [--data-root <p>] [--json]` | 显式建根；非空且非照夜目录 → 拒绝 | 0 / 3 / 6 |
| `zhaoye doctor [--data-root <p>] [--json]` | 只读检查：manifest、JSON、哈希、投影、快照、presence | 0 / 5 |
| `zhaoye identity show [--json]` | 无 `--json` 打印投影；有则打印文档 JSON | 0 / 5 |
| `zhaoye identity history [--limit n]` | 版本列表（默认 20） | 0 |
| `zhaoye identity apply <file.json>` | 读取 `IdentityCommitRequest` 并提交；`--dry-run` 只预览 | 0 / 3 / 4 |
| `zhaoye presence [--release] [--json]` | 显示 owner；`--release` 仅释放本实例 | 0 / 1 |

退出码约定：`0` 成功；`1` 运行时错误；`2` 用法错误；`3` 输入/状态冲突；`4` 授权拒绝；`5` 数据损坏；`6` 存储失败。`--json` 统一输出 `{ ok, data | error }`，错误含 `code`/`action`/`details`。

`identity apply` 的 actor 固定 `adapter_id: 'cli'`；内核提交仍要求请求体自带 `user_confirmed`，CLI 不代替用户确认。

## 13. 实施结论（2026-11-02）

开发前先提交 `M1-执行计划.md`（`6905b67`），用户明确确认默认三条原则，然后在 `codex/m1-identity` 实现。验证命令与统计统一见 02 §1；仅使用临时测试根。

实施偏差与原因：

1. 以 01 I8 与 S-10 为准：活 PID 即使心跳过期也不接管。presence 使用排他短锁串行化获取/心跳/释放，死 PID 可接管；不以普通 rename 冒充跨进程互斥。
2. `doctor(dataRoot)` 独立只读，不建根、不持锁，因此损坏或占用时也可诊断。普通读写经 `createZhaoye` 获取 presence；`close` 等待进行中调用和心跳结束，重复关闭幂等。
3. 普通提交与内核提交、普通回滚与内核回滚分入口。操作日志新增 evidence_refs / confirmation_ref，保留用户确认来源；跨 adapter 的幂等回执不能复用。
4. 提交顺序以 03 §5.3 为准。投影/快照失败返回已提交回执与警告；JSON 替换后结果未知 → COMMIT_UNKNOWN。旧快照缺失不可凭没有正文的操作日志重建；doctor 明确报告。
5. CLI 的 run 变为异步；增加显式 `identity rollback <request.json>`。独立 presence 命令没有实例凭据，`--release` 拒绝释放别人的 owner；持有者经 app.close 释放。
6. 测试按源文件映射编译产物，避免已删除测试的旧 dist 文件被误执行；缺编译产物直接失败。验证入口纳入真实跨进程与 Windows ACL 检查。

限制：Windows 无目录 fsync，不能承诺断电后的目录项持久化；中断初始化或短锁文件本身不完整时返回 LOCKED，需依据 details.path 人工核对，不盲删锁；幂等只覆盖当前及上一轮有界操作日志；跨文件提交不是事务，COMMIT_UNKNOWN 必须先诊断再重试。DSH/MCP 仍是占位，不是 M1 验收范围。SQLite 打包/跨平台 spike 留到 M2 开工前。
