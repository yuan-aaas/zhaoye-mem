# 05 M2 备份库与检索开发设计

> MC-2 至 MC-4 已实现，Mneme 真实库往返已在 Windows 验证。以 [01 架构基线](01-架构基线.md) 的只读边界和 [02 工程与里程碑](02-工程与里程碑.md) 的 M2 退出条件为准。
>
> 2026-11-23 在 Windows / Node 24.14.0 用 `DatabaseSync(path, { readOnly: true })` 执行 `PRAGMA table_info('memories')` 和汇总查询。Mneme 存量库为 WAL，共 2,520 条记忆，活跃 1,360 条、归档 1,160 条、遗忘 0 条。Agent 范围全部为空，只有 1 条带 workspace 范围、5 条带内容历史。另用临时 SQLite 文件通过 WAL、在线备份、恢复读回及 `integrity_check` 验证。

## 1. 交付目标与边界

首个来源是用户选定的 Mneme `memory.db`。照夜为它生成一致性快照，将 `memories` 中的记录转换成通用模型，保留来源、批次、版本、范围与可见性，再由照夜自己的 SQLite 提供检索。新增其他来源时扩展读取器和转换器，存储、查询及返回模型共用。

- 读取源库只通过独立 SQLite 只读连接。源侧迁移、整理、在线记忆搜索、写回和自动同步均在 M2 范围之外。转换器只校验和映射字段，用户偏好类记忆也留在备份域。
- 首版语义覆盖用户授权的 `memories` 主表。原件保留能追溯的源数据。向量、运行台账、用户设置、图谱、Markdown 镜像和文档指针所指的外部文件留在原格式。通用查询只访问已转换和授权的记录。
- 数据库快照保存在照夜数据根，DSH 插件生命周期留到 M4。M2 的验收入口为本地 CLI 和应用门面。

## 2. 文件选取、授权与快照

### 2.1 注册一个来源

用户通过 CLI 选择明确的文件和照夜 `scope_id`，应用分配持久 `source_id`。同一个逻辑源库移动路径时，用已有 `source_id` 重新绑定。另一份独立库注册新 ID。同一源库的一致性快照可作为该来源的历史输入。路径、文件摘要和 Mneme 的 `source` 字段均作为证据或定位信息。

无文件参数时，CLI 仅枚举标准候选。按显式 `MNEME_MEMORY_DIR`、`MNEME_HOME`（兼容 `DSH_MNEME_HOME`）、`~/.mneme/memory/memory.db`、`~/.dsh/memory/memory.db` 检查并去重。候选只有一个时显示该文件供明确选用，多个时要求给出文件路径。已注册来源使用它当前绑定的文件，绑定缺失返回 `SOURCE_UNAVAILABLE`。当前工作环境找到的是旧目录中的 `~/.dsh/memory/memory.db`。

来源注册持久化源文件位置、可备份的 Agent/workspace 范围、显式标签映射，以及是否允许保存整库原件。导入权限和查询权限分别由 app 检查。整库原件可能包含通用表范围之外的数据，选择原件模式时记录对整个文件的授权。只批准部分范围时，暂存物和归档物只包含经批准的数据，见下一节。

来源策略至少定义 `capture_scope`（允许的源 Agent/workspace 集合及是否包含空标签）、`project_map`（源标签组合到照夜项目 ID 的显式映射）、`allowed_sensitivity`（允许的源敏感级别及未知值策略）、`raw_mode`（`sqlite` 或 `scoped_ndjson`）与 `mapping_version`。导入范围必须落在来源授权内。空标签和未知敏感级别默认排除，由操作者分别授予权限。独立的查询授权决定这些已采集记录是否向调用者可见。

### 2.2 生成一致性输入

1. 解析真实路径并确认是已有普通文件。拒绝把照夜目标库、暂存目录或备份原件目录中的文件注册为实时来源，允许通过显式的历史输入入口读取归档物。源文件不存在时终止，保持原路径无写操作。
2. 用 `node:sqlite` 只读打开源。WAL 的读取依赖正常的 SQLite 事务和必要的辅助文件。只读环境无法访问 WAL 时，返回 `SOURCE_UNAVAILABLE`，可改用静态一致性快照。打开过程使用有界的 busy 等待和重试。
3. **整库授权**时，通过 SQLite Online Backup API 写入照夜暂存目录，再以只读方式打开快照。**限定范围授权**时，在源库的一个只读事务里读取允许的 `memories` 行与必要标签，直接生成版本化 NDJSON 导出作为原件，从始至终只落盘授权范围。完整枚举及有效的映射规则是部分授权模式声明覆盖完整的前提。
4. 计算原件 SHA-256，记录开始和完成时间、格式、实际检测到的表结构、范围、行数或扫描终止原因。仅在无法获得可信源侧截至时间时，使用本次读取完成时间，并在元数据中标明它是照夜采集时间。快照后处理使用固定的原件。
5. 将原件与 manifest 放到同一文件系统的批次目录。完成文件写入及校验后原子移动目录，再提交本地批次终态。归档路径为相对照夜数据根的路径，内容始终留在本机。

```text
backup/
  zhaoye.db
  .staging/<batch_id>/
  exports/<batch_id>/
    manifest.json
    source.sqlite | source.ndjson
```

原件 manifest 使用 `contracts/src/backup.ts` 中的 `BackupManifestSchema`。包含批次和来源 ID、范围标识、源格式、转换器版本、采集开始时间、截至时间及其来源、声明覆盖和原件摘要。文件名固定为 `source.sqlite` 或 `source.ndjson`。完整批次的原件必须声明完整覆盖。读取、校验和恢复原件使用相同的路径约束。对源文件不调用 Mneme 的 `createStore()`，其初始化包含写入和迁移。原件、正文和绝对源路径不进入一般日志、提交和公开测试夹具。

## 3. 通用记录及 Mneme 映射

**记录**表示同一来源内的稳定身份。**版本**表示某次规范化后得到的可检索内容。**批次记录**表示某个批次对该记录及其状态的观察，承载来源状态、范围和原件引用。同一版本可被多个批次观察。同一条记录退回曾出现过的正文时复用已有内容版本，观察顺序仍完整保留。

| Mneme 字段 | 通用字段及首版规则 |
|---|---|
| 源实例 + `memories.id` | `source_id` + `native_id`，目标库分配稳定 `record_id`。保留原始 ID 字符串 |
| `type` | `kind`。已知类型映射至同名通用类型，未知非空类型映射为 `other` 并保留 `native_kind`。首版支持偏好、项目、决策、历史、摘要、模式、被否方案、踩坑、约束、文档指针 |
| `title`、`content` | `title`、`body`。校验类型，保留正文及 Markdown，统一换行为 LF。文档类型保留摘要和源指针字符串 |
| `tags`、`importance` | 批次观察的 `metadata_json`，标签验证字符串数组，异常值标记并保留在原件中 |
| `source`、`created_at`、`updated_at`、`occurred_at` | 源来源说明和源时间。合法时间转 UTC，空值或无法解析记为未知并保留原值，不用导入时间冒充源时间 |
| `content_hash` | 保留为 `native_content_hash`。以照夜规范化版本的稳定字节独立计算 SHA-256 |
| `agent_scope`、`workspace_scope`、标签来源、`sensitivity` | 保留原始标签。通过显式映射给出照夜的 `project_id` 和可检索资格 |
| `archived`、`forgotten`、`archived_at` | 保留为源状态。任一标记置位时 `visibility=unavailable`，原因分别记录为归档、抑制或两者。显式授权后可以查看历史 |
| `content_history`、`evidence` | 首版保留原件引用，语义未验证的旧内容不生成确定版本。照夜版本链从首轮成功观察开始 |
| `doc_path`、`_full_content`、`embedding` | 文档路径作为源指针，长载荷和向量保留在原件。通用转换使用 `content` |

`content_hash = sha256(UTF8(stableJson({kind,title,body})))`。时间、标签、归档状态等只写批次观察，避免纯元数据更新产生内容版本。版本复用比较同一 `record_id` 下的摘要及稳定字节。每条观察使用 `batch_id + 表名 + native_id` 指向原件。NDJSON 原件用同一 `native_id` 定位。

导入器检查 `memories`、记录和可见性必需列，以及当前授权策略依赖的范围列。缺列返回 `SCHEMA_MIGRATION_REQUIRED` 和列名，导入批次记为 `failed`，查询继续使用上一完整批次。无法确认记录身份、必要字段损坏或重复 ID 的记录计入失败明细。有成功记录的批次可提交为 `partial`，整表或快照不可读时批次为 `failed`。单行意外类型记录列级诊断及原件引用。

## 4. SQLite 物理表

表名沿用 [03](03-记忆核心技术设计.md) 已有名称。首版用 `batch_records` 表达版本与批次的多对多关联，用 `backup_scope_heads` 定位最近完整批次。记录级当前状态由完整批次的行推导，避免部分导入更新可见版本的指针。

```sql
CREATE TABLE meta (
  key TEXT PRIMARY KEY, value TEXT NOT NULL
);

CREATE TABLE backup_sources (
  source_id TEXT PRIMARY KEY,
  source_kind TEXT NOT NULL,
  scope_id TEXT NOT NULL,
  display_name TEXT NOT NULL,
  policy_json TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE import_batches (
  batch_id TEXT PRIMARY KEY,
  source_id TEXT NOT NULL REFERENCES backup_sources(source_id),
  scope_key TEXT NOT NULL,
  scope_json TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('running','complete','partial','failed')),
  capture_mode TEXT NOT NULL CHECK (capture_mode IN ('live','historical')),
  capture_seq INTEGER CHECK (capture_seq > 0),
  captured_at TEXT,
  captured_at_kind TEXT,
  started_at TEXT NOT NULL,
  finished_at TEXT,
  source_format TEXT NOT NULL,
  converter_version TEXT NOT NULL,
  raw_manifest TEXT,
  raw_sha256 TEXT,
  read_count INTEGER NOT NULL DEFAULT 0 CHECK (read_count >= 0),
  accepted_count INTEGER NOT NULL DEFAULT 0 CHECK (accepted_count >= 0),
  rejected_count INTEGER NOT NULL DEFAULT 0 CHECK (rejected_count >= 0),
  detail_json TEXT,
  UNIQUE (source_id, scope_key, batch_id, status, capture_mode),
  UNIQUE (source_id, batch_id),
  UNIQUE (source_id, capture_seq),
  CHECK (capture_mode = 'live' OR capture_seq IS NULL),
  CHECK (status NOT IN ('complete','partial') OR
    (captured_at IS NOT NULL AND finished_at IS NOT NULL
      AND raw_manifest IS NOT NULL AND raw_sha256 IS NOT NULL
      AND (capture_mode = 'historical' OR capture_seq IS NOT NULL)))
);

CREATE TABLE source_records (
  record_id TEXT PRIMARY KEY,
  source_id TEXT NOT NULL REFERENCES backup_sources(source_id),
  native_id TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE (source_id, native_id),
  UNIQUE (source_id, record_id)
);

CREATE TABLE record_versions (
  version_id TEXT PRIMARY KEY,
  record_id TEXT NOT NULL REFERENCES source_records(record_id),
  kind TEXT NOT NULL,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  content_hash TEXT NOT NULL,
  created_at TEXT NOT NULL,
  UNIQUE (record_id, content_hash),
  UNIQUE (record_id, version_id)
);

CREATE TABLE batch_records (
  batch_id TEXT NOT NULL,
  source_id TEXT NOT NULL,
  record_id TEXT NOT NULL,
  version_id TEXT,
  project_id TEXT,
  search_allowed INTEGER NOT NULL CHECK (search_allowed IN (0,1)),
  visibility TEXT NOT NULL CHECK (visibility IN ('visible','unavailable','deleted')),
  visibility_reason TEXT,
  source_updated_at TEXT,
  raw_ref TEXT,
  metadata_json TEXT NOT NULL,
  PRIMARY KEY (batch_id, record_id),
  FOREIGN KEY (source_id, batch_id) REFERENCES import_batches(source_id, batch_id),
  FOREIGN KEY (source_id, record_id) REFERENCES source_records(source_id, record_id),
  FOREIGN KEY (record_id, version_id) REFERENCES record_versions(record_id, version_id),
  CHECK (visibility <> 'visible' OR version_id IS NOT NULL)
);

CREATE TABLE backup_scope_heads (
  source_id TEXT NOT NULL,
  scope_key TEXT NOT NULL,
  batch_id TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'complete' CHECK (status = 'complete'),
  capture_mode TEXT NOT NULL DEFAULT 'live' CHECK (capture_mode = 'live'),
  PRIMARY KEY (source_id, scope_key),
  FOREIGN KEY (source_id, scope_key, batch_id, status, capture_mode)
    REFERENCES import_batches(source_id, scope_key, batch_id, status, capture_mode)
);

CREATE TABLE backup_operations (
  scope_id TEXT NOT NULL,
  operation_id TEXT NOT NULL,
  adapter_id TEXT NOT NULL,
  request_fingerprint TEXT NOT NULL,
  batch_id TEXT NOT NULL UNIQUE REFERENCES import_batches(batch_id),
  receipt_json TEXT,
  PRIMARY KEY (scope_id, operation_id)
);

CREATE TABLE heat (
  record_id TEXT PRIMARY KEY REFERENCES source_records(record_id),
  hits INTEGER NOT NULL DEFAULT 0,
  last_hit_at TEXT,
  explicit_feedback INTEGER NOT NULL DEFAULT 0
);

CREATE VIRTUAL TABLE record_fts USING fts5(
  title, body, version_id UNINDEXED, tokenize='trigram'
);

CREATE INDEX idx_batches_scope ON import_batches(source_id, scope_key, capture_seq, batch_id);
CREATE UNIQUE INDEX idx_running_live_source ON import_batches(source_id)
  WHERE status = 'running' AND capture_mode = 'live';
CREATE INDEX idx_batch_records_lookup ON batch_records(record_id, batch_id);
CREATE INDEX idx_batch_records_filter ON batch_records(batch_id, project_id, visibility, search_allowed);
```

初始化时启用外键和 WAL。迁移按备份库自己的 schema 版本跑事务，已有 M1 数据根及人格 JSON 路径沿用现状。备份库只在显式写入备份域时创建。版本索引跟随本地事务更新，可由 `record_versions` 重建。历史版本有索引时仍要通过批次、授权与可见性过滤才可返回。启动时校验版本，查询路径遇到损坏须报错。

## 5. 事务、批次与重试

### 5.1 批次的含义

`scope_key` 由规范化的逻辑源范围与映射策略生成。它覆盖所选 Agent/workspace、空标签、敏感度准入及项目映射。影响覆盖的策略变更使用新的 key，当前视图随之切换，旧 key 留作历史。每个来源首版只激活一套导入范围，避免同一记录因不同范围叠加而重复出现。

- **running**：应用已建立请求与批次记录，正在固定源快照或转换。
- **complete**：所有获授权范围已枚举，所有应纳入行都获得有效观察，原件已核对，目标事务已提交。它描述现存采集范围，不提供首次采集前的已删历史。
- **partial**：覆盖不确定或部分记录被拒，已验证的记录可与回执一同保留。完整批次指针保持在之前的 complete。从 partial 产生的观察不推断缺失记录。
- **failed**：读源、校验或发布失败。保存安全诊断和可核对的原件状态，查询不使用失败批次的记录。

只在**同一来源、同一 scope key、且顺序可信的较新完整快照**之间比较缺失。已有记录未出现在新快照时，派生观察 `unavailable/source_absent`，保留旧版本引用并计入缺失数。只有具备可信源删除证据才记录 `deleted`。首次快照、部分批次、未知时间的外部历史输入均不触发缺失推断。实时采集在每个来源上串行，固定原件后分配单调递增的 `capture_seq`。外部历史文件用 `historical` 模式导入，保留历史证据而不推进当前指针。有些行因权限或标签离开范围，按范围状态处理，无法确认实际删除时统一采用 `source_absent`。

批次回执包含 `request_id`、`operation_id`、`batch_id`、状态、来源和范围、截至时间与时间来源、枚举数、有效数、拒绝数、范围排除数、新记录数、复用版本数、新版本数、缺失推断数、上一个完整批次 ID 和原件摘要。枚举数与行级计数按实际输入计算，派生缺失观察单独计数。限定范围模式的诊断只保留获授权的内容和计数，原始逐行错误按安全字段汇总。

### 5.2 两层幂等与失败恢复

1. app 先核验权限和同一 `scope_id + operation_id` 的请求指纹，含来源、绑定的范围和采集模式。相同请求与调用适配器回放原终态回执，运行中的返回该批次状态，不重复采集。不同参数冲突，跨适配器回放拒绝。修正冲突、失败或部分导入后用新 `operation_id` 发起重新采集。
2. 采集及转换发生在目标库写事务之外。只有固定原件可用、范围和记录都已校验后，开启发布事务。
3. 发布事务写记录、内容版本、批次观察与 FTS，保存终态和回执。满足完整批次条件时同事务切换 `backup_scope_heads`。重复内容复用版本，即使来自不同批次。提交错误回滚业务行，另行尝试把仍是 running 的批次记录为 failed。提交结果未知时按操作 ID 核对已持久化回执，禁止盲重放。
4. 成功回执只在可重开读取后返回。崩溃恢复扫描遗留 running 批次，核对最终目录、原件摘要和库内回执。未发布的原件可保留用于诊断，批次标 failed；终态已提交的按已保存回执恢复。目标完整指针只跟随原子提交。失效暂存物按状态清理，已被回执引用的原件需先通过一致性核对。

## 6. 授权、检索和证据

**导入边界。** 源文件操作身份必须拥有绑定来源与范围的导入权限。导入空标签行需要来源配置显式授权。已批准采集但仍无明确项目映射的非空标签，可以保留原值并标为不可检索。敏感级别需明确准入。正文或标题中的项目名称仅作为内容。明确被策略排除的行不计入失败数。个别行的范围值损坏时计入失败数，有其他有效记录时批次降级为 partial。限定范围模式只归档能确认范围与敏感度授权的条目。

**查询边界。** app 把请求范围与调用者授权求交并验证 `scope_id`。请求超出授权返回 `OUT_OF_SCOPE`。通配符只在已授权集合内展开。无项目归属的记录还要求独立的 `include_unassigned` 查询授权。授权条件在 SQL 候选集中落实，正文、摘要、计数、批次列表和历史详情都沿用同一口径。查询当前头时重新评估源策略。同范围内，用 `capture_seq` 找该记录较新且已验证的最新观察。它显示归档、抑制、撤权或重新归属到未授权项目时，收窄普通结果。完整快照及其历史仍保留，历史读单独检查历史权限和当前来源授权。

**检索。** 默认只查每个来源最近完整批次中可见且获授权的观察。部分批次的有效行仅由显式指定批次的查询或详情读取返回，继续验证行级授权和当前可见性策略。缺少完整批次或已有更新的 partial 时，返回覆盖不足的状态与可用批次信息。归档和其他历史通过显式范围授权读取，不出现在默认检索和会话注入中。

- 在已授权候选内组合标题、正文 FTS，首版将用户输入编码为字面短语。全文检索先核对候选版本和对应索引条目，发现缺行、重复或内容不一致时返回 `INTEGRITY_FAILED`。1–2 码点的短词用参数化 `instr` 直接查正文。空查询拒绝。冷数据始终允许按内容召回。
- 首版相关性排序按标题完全匹配、标题包含、正文命中分档，同档按源更新时间倒序（未知排最后）和稳定记录 ID 升序。排序只依赖匹配候选本身。默认返回 5 条、上限 20。游标绑定过滤条件、授权口径、排序版本及批次视图。查询范围、授权或相关批次观察发生变化时，要求从首屏重新查询。
- 每条命中返回 `record_id`、`version_id`、来源、项目、所属批次、源更新时间、截至时间及类型、摘要、内容摘要哈希、可见状态。批次聚合覆盖信息与分页分开计算，兼容 `coverage` 统一状态。当有更多结果时返回游标。若读取到末页但来源缺失或部分，则标为 partial 并给范围原因。空结果、范围不足和库损坏分别表达。
- 普通查询保持只读。热度通过明确的反馈路径写入，避免普通检索或分页改变同一个游标的排序输入。首轮排序可用与批次数据同一视图的固定信号。

## 7. 包、端口与可运行入口

| 位置 | 实现职责 |
|---|---|
| `contracts` | 新增严格的 `SnapshotSourcePort`、`BackupDb`、规范化记录、导入范围、回执以及查询请求/结果 schema。保留现有 `SourcePort.list/read` 签名，避免使已有逐条端口承担快照语义 |
| `storage` | 文件路径和原件存储、Mneme 文件只读访问及快照、SQLite schema/migrations、备份事务与范围内 SQL、FTS、版本与批次校验。SQLite 绑定只出现在这一层 |
| `core` | 通用备份服务、纯 Mneme 字段映射、覆盖状态和版本规则。读取器负责行，转换器负责值，core 通过 contracts 访问存储 |
| `app` | 组合来源与备份库，校验角色、范围、预算及幂等，统一公开 `importSnapshot`、`listImportBatches`、`searchBackup`、`getBackupRecord`、`verifyBackup`，集成只读 doctor |
| `cli` | 提供显式来源绑定、导入、列表、检索和校验入口，复用 app 与既有 JSON 退出码形态 |

快照端口以 `capture(request)` 返回固定原件的元数据和受控可迭代的源行。返回源行与原件使用相同的读取视图，转换器可独立用合成行测试。备份端口提供打开与迁移、发布批次、检索、详情、原件核对及在线数据库快照。应用门面承担写路径，日常查询和诊断在备份域缺失时明确显示未初始化。

MC-2 已实现 `openBackupDb` 和 `verifyBackupSnapshot`。后续应用层在取得数据根 presence 后调用 `recoverInterruptedBatches`。批次发布前的可修正问题允许重试同一运行批次。应用确认停止本次采集时调用 `failBatch` 保存终态回执。查询与 Mneme 源读取入口分别由 MC-4 与 MC-3 补齐。

CLI 入口复用现有 `--data-root`、`--json` 和退出码约定。数据根通过 `zhaoye init` 初始化。

```text
zhaoye backup source add --kind mneme --file <memory.db> --policy <policy.json>
zhaoye backup import --source <source-id> --operation-id <id> [--historical-snapshot <file>]
zhaoye backup batches --source <source-id>
zhaoye backup search <query> --source <source-id> [--unassigned] [--limit <number>] [--cursor <cursor>]
zhaoye backup record <record-id> --source <source-id> [--batch <batch-id>] [--unassigned] [--history]
zhaoye backup export-mneme --source <source-id> --out <new-sqlite-file> [--unassigned] [--history]
zhaoye backup verify
```

策略文件使用以下字段。示例明确允许采集无归属和敏感度未知的记录，使用限定范围的 NDJSON 原件。按库授权保存完整 SQLite 原件时设 `rawMode` 为 `sqlite`。有标签的记录通过 `projects` 将 `agent` 和 `workspace` 组合映射到指定 `projectId`。使用 `--unassigned` 查询已授权的无归属记录，使用 `--history` 才包含已获授权的归档或遗忘记录。显式指定 `--batch` 还要求历史读取权限，并沿用当前来源策略范围。

```json
{
  "rawMode": "scoped_ndjson",
  "includeUnassigned": true,
  "includeUnknownSensitivity": true,
  "projects": [
    { "agent": null, "workspace": "example-workspace", "projectId": "example-project" }
  ]
}
```

反向导出创建独立的 Mneme `memories` 表文件，保留通用字段和已捕获的 Mneme 元数据。正文采用统一的 LF 换行。向量、侧表、历史正文和内部运行状态由整库快照保留，独立交换文件覆盖主表映射的字段。真实库验证结果见 [02 的 M2 记录](02-工程与里程碑.md#m2-备份库与检索)。

## 8. 备份、恢复和诊断

目标库的 MC-2 备份包含在线 SQLite 快照和声明范围内的原件文件。先获取 SQLite 快照，将包内快照转为独立的主文件，再以快照中已提交的批次清单确定需要打包的原件，逐个核验 SHA-256。目标为新目录，最终清单是包的完成标记。中断后缺少该标记的目录无法通过验证，重试使用新目录。可用 `verifyBackupSnapshot` 在独立目录打开快照并检查主库、批次和原件。覆盖原目录的迁移与运维命令留在 M5。

`verifyBackup` 检查库版本、数据库结构、外键、版本摘要、完整批次指针、原件路径与摘要、批次计数和 FTS 与版本的对应关系。doctor 默认读取摘要诊断，深入验证可单独触发。按 [03 错误模型](03-记忆核心技术设计.md#6-错误模型与恢复) 区分源不可用、部分覆盖、拒绝访问、结构不支持、存储失败和数据损坏。

## 9. 实施与验收

1. **MC-2**：实现通用库 schema、迁移、约束、事务、备份恢复及端口。验证 Windows、Linux、macOS 的目标 Node 24 构建和 SQLite FTS/备份能力，驱动策略为首版 `node:sqlite`，绑定限制在 `storage`。
2. **MC-3**：实现 Mneme 源选择、只读快照、字段映射与批次原件，完成导入和回执，再用本机数据在独立测试数据根做两次导入。用本次采集 manifest 的计数判定差异，历史统计只供参考。
3. **MC-4**：实现同口径授权、分页、覆盖级别、冷数据召回、短词兜底及应用入口，使用由真实样本验过的查询形状和可提交的合成夹具跑回归。

| 验收场景 | 应观察到的结果 |
|---|---|
| 缺文件、双路径候选、旧 schema | 缺文件明确拒绝，多候选要求指明，按实测列集合识别兼容 schema |
| 活动 WAL 与源库一致性 | 在线采集包含快照点内已提交记录，源文件无业务写入或 schema 变更，目标原件校验通过 |
| 首次及重复导入 | 记录与原件计数对得上。同 operation 回放，新 operation 重采相同内容只增加批次关联。改正文增版本，改归档或标签只增观察 |
| 部分、错误及崩溃 | 部分导入保留上一个完整指针。任一发布错误回滚目标行。原件落盘、事务提交和返回回执各中断点都能重开核对 |
| 缺失、删除、归档和恢复 | 完整可比快照的缺失可追踪。只有可信证据才标删除。归档及遗忘默认隐藏，恢复可见复用原版本 |
| 范围与检索 | 错源、错项目、无归属与未知标签按授权拒绝或隐藏。支持中文短词、冷数据和稳定分页。正常空结果与损坏可区分 |
| 备份与恢复 | 在独立目录恢复后读取同一批次和版本，完整原件摘要匹配。缺件、摘要不符、索引缺失可诊断 |
