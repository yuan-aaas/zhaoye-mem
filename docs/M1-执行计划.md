依据：01 架构基线、03 技术设计、04 M1 开发设计。用户已确认采用 04 中三条默认安全原则。

## 交付顺序

1. 契约：移除旧事件信封；严格身份 schema、稳定序列化、字段上限、错误模型、存储端口与默认值。先冻结可测试的契约。
2. 存储：数据根守护、原子写、版本快照、幂等记录轮转、presence 单活与恢复；覆盖中文路径和失败注入。
3. 领域：受范围约束的读取/预览/提交/回滚；CAS、幂等、确认凭据、逐条更新与确定性投影。
4. 应用与 CLI：唯一组合根、生命周期、只读 doctor、init/identity/presence 命令与 JSON 错误输出。
5. 验收：构建、类型、lint、依赖边界、至少 30 个有效测试；PowerShell 驱动真实跨进程竞争及 CLI 全链路。
6. 收尾：回写 02/03/04 与 README，记录验证证据和限制，提交并推送独立分支。

## 开发前消除设计矛盾

- 活 PID 即使心跳过期也不自动接管，以 01 I8 和 04 S-10 为准。
- presence 获取必须用排他创建与短期锁串行化，不能用读后 rename 假装跨进程互斥；heartbeat/release 同样受锁保护。
- JSON 是唯一事实源。提交后派生投影失败返回已提交回执与 warning；主文件 rename 后持久化结果不确定则 COMMIT_UNKNOWN，禁止返回“未写入”。
- 版本/操作记录不能凭空恢复历史内容。当前版本缺快照可由当前 JSON 重建，旧快照缺失必须显式报告不可恢复。
- 幂等先校验 actor/scope，再按 operation_id 复用原回执；跨 adapter 复用拒绝。不得利用幂等路径绕过授权。
- 只读 doctor 在损坏或被占用时也能运行，不创建根、不获取 presence、不重建文件。
- 普通身份更新和内核更新分别暴露方法；CLI 只有显式用户确认凭据才能进入内核方法。

## 验收与边界

覆盖初次/重复初始化、非空目录保护、损坏拒绝、CAS 竞争、幂等重试、内核无确认拒绝、版本回滚、快照保留、日志半行与轮转、活进程不抢占、死进程接管、关闭后写拒绝、CLI 完整闭环。只操作测试临时数据根，不写用户真实身份数据。

M2 SQLite、备份导入、资产、DSH/MCP 宿主、模型调用、发布打包不在本阶段。SQLite 驱动 spike 留到 M2 前，不作为 M1 功能完成证据。
