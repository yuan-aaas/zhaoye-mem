# 工程骨架与业务填充路线

> 当前数据域、存储格式和外部管理框架职责以[外部管理框架与记忆核心设计](外部管理框架与记忆核心设计.md)为准。本文中 journal/提交序列器驱动的旧路线已被取代。

> **定位**：记录当前仓库已经搭好的工程骨架、各目录职责和后续业务实现顺序。
> **当前记忆与框架设计真源**：[外部管理框架与记忆核心设计](外部管理框架与记忆核心设计.md)；**T0 工程状态**仍以本文为准。
> 本文只记录“当前有什么、接下来填什么”，不重复定义架构不变量和接口细节。

## 1. 当前状态

T0 工程骨架已完成并通过本机验证。`storage`、`core`、`app`、`adapter-kit` 与插件中的业务实现仍属于后续里程碑；包入口和 smoke test 不代表业务功能已经完成。

验证结果：

- `pnpm install --frozen-lockfile` 成功。
- `scripts/verify.ps1` 成功：8 个工作区包版本一致，源码和测试编译、类型检查、Biome、dependency-cruiser 及 12 条测试通过。
- 受限 Windows 沙箱中 pnpm 递归命令可能触发 `spawn EPERM`；此时用上述 PowerShell 验证脚本。

## 2. 骨架目录清单

```text
zhaoye/
├─ package.json                  根脚本、开发依赖、Node/pnpm 版本约束
├─ pnpm-workspace.yaml           packages/* 与 plugins/* 工作区
├─ pnpm-lock.yaml                唯一依赖锁文件
├─ tsconfig.base.json            全仓 TypeScript 编译基线
├─ tsconfig.arch.json            架构扫描时将包名解析到源码入口
├─ biome.json                    格式和 lint 规则
├─ .dependency-cruiser.cjs       包边界与依赖方向规则
├─ .npmrc / .gitignore           pnpm 与仓库忽略规则
├─ README.md                     安装、验证和文档入口
├─ scripts/
│  ├─ check-versions.mjs         检查 8 个包版本一致
│  ├─ run-tests.mjs              导入编译后的测试文件，不 spawn 子进程
│  └─ verify.ps1                 Windows 沙箱验证兜底
├─ packages/
│  ├─ contracts/                 共享 schema、类型、错误码、预算与端口
│  ├─ storage/                   数据根、原子文件、日志、序列器、presence
│  ├─ core/                      identity、memory 与路由索引
│  ├─ app/                       AssistantService 与组合根
│  ├─ adapter-kit/               宿主无关的适配器共用逻辑
│  └─ cli/                       命令行入口；当前仅有 --version 骨架
├─ plugins/
│  ├─ dsh/                        DSH 宿主插件入口与 host 占位
│  └─ mcp/                        MCP 服务入口占位
├─ tests/
│  ├─ adapter-conformance/        假宿主和一致性检查骨架
│  └─ integration/                集成测试目录
└─ presets/                       kernel 与 persona 模板占位
```

8 个包均有 package manifest、构建/测试 TypeScript 配置、源码入口和 smoke test。`contracts` 当前已经提供 EventEnvelope 的 Zod schema，以及其余领域契约的初始类型；这些初始类型仍需按架构文档逐项定稿。

## 3. 每个包后续要填的业务

| 顺序 | 包/目录 | 主要业务内容 | 完成时应能证明 |
|---|---|---|---|
| 1 | `packages/contracts` | 对齐事件闭集、identity/memory/query/receipt/presence 字段、错误语义、预算和端口签名 | schema 与类型能拒绝非法数据；跨包调用只依赖公开契约 |
| 2 | `packages/storage` | 数据根守护式初始化、原子写、追加日志、提交序列器、presence、投影重建 | 撕尾恢复、中段损坏拒绝、单写者冲突、提交序列连续 |
| 3 | `packages/core` | safety-kernel 用户发起的 propose/apply/verify；character-profile 版本化读写；memory CRUD 与路由索引/rebuild | 内核受保护；性格画像可留证据地迭代；记忆 CRUD 可回放，查询能定位并召回 |
| 4 | `packages/app` | AssistantService、createZhaoye、权限与生命周期、预算断言、任务账本 | 所有业务写入经过唯一门面，恢复行为符合状态机 |
| 5 | `packages/adapter-kit` | persona/prompt 装配、receipt 校验、notice 渲染、project 映射、tool schema | 多个宿主共用同一逻辑，不复制领域规则 |
| 6 | `packages/cli` | init、doctor、presence、migrate、export 命令 | 命令只编排门面并给出明确成功/失败反馈 |
| 7 | `plugins/dsh` | 真实宿主生命周期、能力探测、工具注册、会话注入、Worker 接入 | DSH conformance 和真机验收通过 |
| 8 | `plugins/mcp` | MCP tools/resources 与错误、能力映射 | MCP 请求复用 app 服务并通过一致性验证 |
| 9 | `tests/` | 重放、跨进程 presence、身份修复、预算拦截、首次初始化和适配器一致性 | 对应架构成功判据都有自动化证据 |

## 4. 推荐实施顺序

### 第一步：定稿 contracts

先逐项对照[架构设计](架构设计.md)，确认字段、必填/可选约束、错误码和端口行为。若接口需要改变，先更新契约和对应架构说明，再开始依赖它的实现。

### 第二步：完成 M1 存储内核

先保证安全写入和可恢复，再实现上层业务。建议按原子文件与数据根 → journal → sequencer → presence → projections 的顺序实现，并先补失败注入测试。

### 第三步：完成 M2 记忆核心

用已验证的 storage 实现安全内核、可迭代性格画像、memory CRUD、路由索引和预算唯一断言。M2 不实现对话蒸馏；记忆核心只保证存取和一致性。同步补充回放与查询测试。

### 后续认知框架

在记忆 CRUD 稳定后，再实现外部认知框架：读取近期事件、蒸馏并分类、关联证据、处理冲突，按策略更新性格画像或提交记忆变更。认知框架不得绕过 AssistantService，也不得修改安全内核。

### 第四步：完成 M3 门面和 CLI 基础命令

建立唯一组合根和 AssistantService，再实现 CLI 的 init/doctor/presence。适配器不直接访问 storage 或 core 内部实现。

### 第五步：完成 M4 DSH 插件

确定并接入真实 DSH API，把所有宿主依赖收敛在 `plugins/dsh/src/host.ts`，然后逐项跑 conformance 与真机验收。

### 第六步：扩展外部入口和运维能力

按需要实现 MCP、迁移、导出和外部来源。每个入口只增加宿主映射，不改变核心业务规则。

## 5. 每个业务切片的交付要求

每次填充一个可运行的业务切片，并同时提交：

1. 所属包的实现与公开 API 更新。
2. 成功、失败和边界测试；涉及文件或进程时增加对应故障测试。
3. 架构规则验证，确认没有越层依赖或绕过唯一写入口。
4. 对应里程碑的 DoD 结果和未解决限制。
5. 若契约或架构决定变化，更新[架构设计](架构设计.md)或新增决策记录。

完成一个切片后运行 `pnpm verify`；受限 Windows 环境运行 `./scripts/verify.ps1`。不以“入口存在”或“包能编译”作为业务完成的依据。
