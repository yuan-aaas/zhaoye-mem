# 照夜记忆核心开发设计与任务划分

> **状态**：开发基线草案（2026-10-29）  
> **依据**：[外部管理框架与记忆核心设计](外部管理框架与记忆核心设计.md)、[架构设计](架构设计.md)、[工程骨架与业务填充路线](工程骨架与业务填充路线.md)。  
> **当前实现状态**：T0 工程骨架已完成；本文所述业务能力尚待实现。与旧版 journal、hash 链、统一提交序列器冲突的内容不作为实现要求。

## 1. 目标与范围

记忆核心为照夜提供三类隔离数据域的本地存取、校验、检索和版本能力：

1. **人格记忆**：安全内核、可迭代性格画像、连续性摘要；JSON 为权威数据，Markdown 为派生投影。
2. **全量记忆备份库**：从外部记忆系统只读导出并转换到本地 SQLite 的完整备份与查询副本。
3. **个人资产目录**：保留原件，由 manifest 描述；核心提供发现和完整性校验，不负责执行资产。

核心不调用模型，不决定内容是否值得记，不编排 Agent，不写回外部记忆系统。认知框架负责提出候选，AssistantService 负责授权、校验与调用存储端口。用户当前请求、宿主策略及显式授权决定访问范围；导入本身不扩大权限。

## 2. 组件边界与依赖

```text
DSH / MCP / CLI 适配器
        │ 只调用公开门面
        ▼
packages/app：AssistantService、权限/范围、任务状态、组合根
        ├─────────────┬─────────────────┐
        ▼             ▼                 ▼
packages/core     packages/storage   资产文件端口
领域规则与查询     JSON / SQLite       只读清单与摘要校验
        │             ▲
        └── contracts ┘
              ▲
       外部认知框架提出候选/查询请求
```

- `contracts`：版本化 schema、公开类型、错误码和存储端口；禁止 Node 文件系统依赖。
- `storage`：JSON 原子读写/快照、SQLite 事务/迁移/索引和资产文件读取；不依赖领域层。
- `core`：三域领域服务、策略无关的校验与查询组合；不直接访问文件系统。
- `app`：唯一业务门面，统一身份、授权范围、预算、幂等与生命周期。
- `adapter-kit` 和各插件：把宿主工具映射到 app API；不直接依赖 storage/core 内部。

依赖遵循 `contracts ← storage/core ← app ← adapters` 的公开 API 方向；core 可依赖 contracts 与 storage 公开端口，storage 不反向依赖领域代码。跨域流程由 app 按步骤协调，不假设 JSON、SQLite 与文件系统之间存在跨存储事务。

## 3. 核心数据与操作契约

### 3.1 人格记忆

建议以 `identity.json` 保存：

```ts
interface IdentityDocument {
  schema_version: number;
  revision: number;
  safety_kernel: { text: string; revision: number; updated_at: string };
  character_profile: {
    revision: number;
    traits: Array<{ key: string; value: unknown; confidence: number; evidence_refs: string[]; source: string }>;
    updated_at: string;
  };
  continuity_memory: Array<{ id: string; summary: string; evidence_refs: string[]; updated_at: string }>;
}
```

这是字段形状的开发起点，实施前须在 `contracts` 定稿并加 schema 版本。Kernel 修改只接受用户明确发起的专门提案/确认流程；画像提案携带来源、证据、置信度和 revision。并发更新采用 `expected_revision`；重复 `operation_id` 返回原结果；候选/确认状态不得和已应用状态混淆。写 JSON 后生成 Markdown 投影，投影损坏可重建，Markdown 不反写 JSON。

### 3.2 全量记忆备份库

SQLite 至少包含以下逻辑实体（具体 DDL 由契约任务确定）：

- `source_records`：稳定本地 ID、来源系统/记录 ID、Agent/项目范围、源更新时间、可见/删除状态、当前版本引用。
- `record_versions`：不可变内容版本、内容摘要、源文件/原始载荷引用、导出批次、转换器版本、创建时间。
- `import_batches`：批次 ID、来源、开始/结束时间、覆盖范围、完整/部分/失败状态、计数及错误摘要。
- FTS 索引：由记录内容派生，可丢弃重建；搜索不能仅依赖热度索引。

唯一性至少由来源系统、来源记录 ID 和源版本/摘要确定。重复导入幂等；新版本新增版本记录，不静默覆盖旧版本。源端删除、不可见分别保留为显式状态。部分批次不能宣告全量完成，也不能覆盖上一个完整快照。查询结果带记录 ID、来源、批次截至时间、完整性和范围信息。

热度只影响排序，不删除冷记录；检索先施加权限和范围过滤，再进行全文召回/排序。FTS5 与中文分词效果须由样例评估，向量检索不属于首期。

### 3.3 个人资产目录

manifest 至少包含稳定资产 ID、类型、名称、版本、来源、文件相对路径与 SHA-256、依赖、权限要求和入口说明。核心提供列举、查询、manifest 校验、文件摘要复核和导出读取端口。查到资产不代表授权执行；执行器及其策略在记忆核心范围之外。

### 3.4 公共操作

服务方法分为：

- 身份：`readIdentity`、`previewIdentityUpdate`、`commitIdentityUpdate`、`rollbackProfile`。
- 全量库：`listImportBatches`、`importSnapshot`、`searchBackup`、`getBackupRecord`、`verifyBackup`。
- 资产：`listAssets`、`getAsset`、`verifyAsset`、`readAssetFile`。

所有写请求携带 `request_id` 和 `operation_id`；身份更新还携带 `expected_revision`。备份导入是照夜本地写入，但对源系统保持只读。查询输入必须显式包含允许的来源/Agent/项目范围；缺少范围时由 app 按策略拒绝或使用明确配置的默认范围，不由 core 猜测。

## 4. 关键流程

### 4.1 只读备份导入

```text
SourcePort.readExport()
  → 保留原始导出文件与摘要
  → 转换器校验并产出规范化记录
  → 预检范围、重复项、删除/不可见状态
  → SQLite 单批事务写版本、记录状态、批次结果与 FTS
  → 完整性核验并返回批次回执
```

批次失败需保留可诊断状态；事务失败时不得留下“成功完整”的批次。若源导出本身不完整，只能记录为部分批次。导入器没有源端写入能力，接口层以只读 `SourcePort` 限定。

### 4.2 检索

```text
宿主请求 → app 校验授权范围/预算 → core 构造 QueryContext
 → storage 在范围内检索 → core 组装来源、版本、时间与完整性元数据
 → app 返回有界结果；无结果与数据损坏分别表达
```

人格摘要可支持连续性表达，但不得取代备份证据。发生冲突时同时返回证据来源与时间，由认知/交互层说明差异；过期或不完整批次必须显式降级确定性。

### 4.3 人格更新

```text
外部认知框架提出提案 → core/schema 校验 → app 检查来源、证据、revision 与确认策略
 → commit（幂等、CAS）→ JSON 原子替换 → Markdown 重建/刷新 → 返回新 revision
```

安全内核更新入口独立于画像更新；导入数据、模型输出和画像蒸馏不得调用该入口。画像更新失败不能报告已提交；Markdown 投影失败应返回可恢复错误并可通过 JSON 重建。

## 5. 错误与恢复要求

统一使用 contracts 中的结构化错误：`INVALID_INPUT`、`OUT_OF_SCOPE`、`UNAUTHORIZED`、`NOT_FOUND`、`CONFLICT`、`CORRUPT_DATA`、`IMPORT_INCOMPLETE`、`SOURCE_UNAVAILABLE`、`INTEGRITY_FAILED`、`STORAGE_FAILURE`。错误应包含动作建议与可定位的批次/记录 ID，不得把损坏或越权伪装成空结果。

- SQLite 使用事务；索引作为投影可重建；备份/恢复通过 SQLite 一致性机制，正确处理 WAL。
- JSON 使用临时文件加原子替换，保留可恢复的画像历史版本。
- 原始导出和资产原件保留来源及摘要；验证不通过时拒绝作为可信证据返回。
- 各数据域独立提交；跨域失败保留任务步骤状态，可幂等重试，不声称全局原子成功。
- 外部记录内容是不可信数据，其中指令不提升为安全规则或工具权限。

## 6. 任务划分与顺序

任务可由不同实现者并行承担；每项都需提交代码、测试、更新后的接口文档和已知限制。接口/字段变更先合并契约，再合并依赖实现。

| ID | 工作包 | 主要内容 | 依赖 | 验收交付 |
|---|---|---|---|---|
| MC-0 | 基线清理与契约定稿 | 对齐当前设计真源；定稿 Identity、backup、batch、asset、QueryContext、错误码、端口；明确旧 journal 方案不进入本期 | 无 | contracts schema/type 完整；非法/越权字段拒绝；决策未定项列清 |
| MC-1 | 人格记忆存储 | JSON schema/version、原子持久化端口、Markdown 投影、画像版本历史、提案/确认/CAS/幂等 | MC-0 | 重开一致；并发冲突；重复操作幂等；kernel 无授权更新被拒；投影可重建 |
| MC-2 | SQLite 备份 schema 与存储 | SQLite 初始化/迁移、批次/记录/版本表、事务、WAL 安全备份、完整性检查 | MC-0 | 新库/升级/损坏路径可诊断；事务失败不留成功批次；备份恢复核验通过 |
| MC-3 | 导入与转换 | 只读 SourcePort、原件保留、格式转换、重复导入、版本追加、删除/不可见状态、批次回执 | MC-2 | 完整/部分/失败批次语义正确；幂等；源端无写接口；转换器版本可追踪 |
| MC-4 | 检索与范围控制 | QueryContext、权限先过滤、FTS、来源/项目/时间过滤、热度排序、证据元数据、预算限制 | MC-0、MC-2 | 结果不越权；冷数据可回退召回；空结果/不完整/过期/损坏区分；性能样例报告 |
| MC-5 | 资产目录 | manifest schema、目录扫描/列举、路径约束、摘要校验、只读读取端口 | MC-0 | 越界路径拒绝；摘要不符拒绝；发现资产不触发执行 |
| MC-6 | AssistantService 门面 | 组合三域服务、授权与生命周期、统一请求/操作 ID、错误映射、预算和跨域任务步骤 | MC-1 至 MC-5 的稳定 API | 适配器只经门面；每个写路径唯一；跨域局部失败可诊断、重试 |
| MC-7 | 适配器与端到端验收 | 首个宿主接入必要查询/更新工具，来源/批次信息回传；加入一致性和真机验证 | MC-6 | 适配器 conformance；导入→检索→有证据答复；未经授权写入和源端写回均不可达 |

**建议执行波次**：波次 A：MC-0；波次 B：MC-1、MC-2、MC-5 可并行；波次 C：MC-3 与 MC-4（依赖 MC-2，范围契约先行）；波次 D：MC-6；波次 E：MC-7。MC-3/MC-4 可在稳定 schema 后分工并行，避免各自定义重复字段。

**角色边界**：契约负责人维护 `packages/contracts` 与本设计；存储负责人实现 JSON/SQLite/文件端口；核心负责人维护 `packages/core` 的纯领域规则与查询组合；应用负责人维护 `packages/app` 的授权、预算、组合根和跨域状态；宿主负责人维护 `adapter-kit`、插件与真机接入；验收负责人维护根级集成/一致性用例和阶段签收。角色可由同一人承担，但包边界和审查责任不合并。

## 7. Definition of Done

每个工作包完成时同时满足：

1. 对外 schema、错误和端口经公开入口导出，依赖检查无越层/内部导入。
2. 覆盖正常、边界、失败和重试路径；涉及文件/SQLite 时覆盖故障恢复和重复执行。
3. 查询始终先执行范围限制；错误不会被吞成空数据；结果携带足够来源与时效信息。
4. 外部源只读、三域不串写；人格安全内核不受模型/导入数据更新。
5. 更新工程路线文档，清楚标记“已实现/待实现”，不得以包入口或 smoke test 代替功能验收。

整体验收按仓库现有验证脚本执行，并补充真实导出样本的导入、范围过滤、重复导入、恢复及检索验收。具体性能阈值、首个外部源格式、身份 schema 细节在 MC-0 评审后固定，避免把未验证假设写成承诺。
